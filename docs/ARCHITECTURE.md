# 架构与数据流

## 三源分工

| 源 | 规模 / 跨度 | 承担实验 | 是否公开原始数据 |
|---|---|---|---|
| A · Kaggle LinkedIn Job Postings | 2023-12 ~ 2024-04（约 5 个月） | E1 技能抽取评测（外部平台标注作金标准）、E2 共现与聚类 | 否（CC BY-SA 4.0） |
| B · HF 日级抓取快照 | 2023-03 ~ 2026-11（36 个有效观测月） | E3 趋势预测、E4 Spark 可扩展性 | 否（OpenRAIL-M） |
| C · 自建合规爬虫 | 2026-11-15，2,001 条去重岗位 | E7 时效性 / 跨平台迁移验证、系统实时岗位看板 | 否（第三方内容与个人信息） |

A 源跨度短且无连续时间轴，**不承担趋势建模**；E3 全部由 B 源提供月度技能热度序列。

## 双库设计

```
thesis_skill（结果库，SQLite / MySQL 8）
  ├── E1-E6 实验结果表 12 张
  ├── 用户 / 角色 / 日志等业务表
  └── 导入基线 1,465 行（论文 5.8 节实测口径）

thesis_crawl（采集库，与结果库并列）
  ├── jobs_c           去重岗位
  ├── skill_freq_c     技能频次（pandas 与 Spark 双口径）
  └── source_c_meta    采集元信息与合规声明
```

分离的目的是：实时采集数据会随后续采集变化，不能混入论文已固定的实测凭证。
Flask 业务代码通过 `source_c.py` 只读访问采集库，账号权限按 SELECT / INSERT / UPDATE / DELETE 分离。

## 处理链路

1. **准备**：A 源解析平台技能标注表、B 源日级快照聚合为月度技能热度（36 个有效观测月）。
2. **Spark 批处理**：Parquet 分区读取、`COUNT(DISTINCT job_id)` 技能频次聚合、与 pandas 结果交叉校验（Top15 完全一致）。
3. **实验 E1–E7**：抽取评测 → 聚类/关联规则 → 多模型滚动原点预测 → 可扩展性 → 系统功能测试 → MySQL 实测 → C 源迁移验证。
4. **入库**：结果写入 `thesis_skill` / `thesis_crawl`。
5. **系统**：Flask + Jinja2 + ECharts 提供登录注册、管理员后台、组合筛选、可视化与 CSV 导出。

## 安全实现

- 口令哈希使用 Werkzeug `scrypt`；会话密钥与演示口令从环境变量读取；
- 所有用户输入走参数化 SQL；`db_backend.py` 用兼容层抹平 SQLite `?` 与 MySQL `%s` 的差异；
- 两级角色（管理员 / 普通用户），数据库账号按最小权限分离；
- C 源采集不登录、不绕过风控（详见 `NOTICE.md`）。
